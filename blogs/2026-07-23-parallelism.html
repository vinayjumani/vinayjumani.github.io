Scaling ML Models: Data, Tensor, and Pipeline Parallelism Explained

July 23, 2026 Distributed Training, LLMs, Systems, GPU 18 min read

Introduction

Prerequisites: This post assumes you know what a forward pass, backward pass, and gradient descent update are. No prior distributed-systems knowledge is needed - every collective operation and every splitting strategy is built up from scratch.

A single NVIDIA A100 has 80GB of memory. A 70-billion-parameter model, stored just as FP32 weights, needs 70B × 4 bytes = 280GB - it does not fit on one GPU, and that is before you count the optimizer states and activations needed to actually train it. Training GPT-scale models is therefore not a "run it and wait" problem; it is a systems problem of splitting a single mathematical computation across dozens, hundreds, or thousands of GPUs while keeping every one of them busy.

This post walks through the four main strategies used to make that split - data parallelism, tensor (model) parallelism, pipeline parallelism, and ZeRO - plus the two techniques that make all of them cheaper to run: activation checkpointing and mixed precision training. The goal is to go from "what does data parallel mean" to "why does Megatron-LM split the weight matrix column-wise instead of row-wise" in one sitting.

Background: Where Does All the Memory Go?

Before splitting anything, it helps to know exactly what is competing for GPU memory during training. The DeepSpeed ZeRO paper splits this into two buckets.

Model states - memory needed regardless of batch size: the parameters themselves, their gradients, and the optimizer states (for Adam: momentum and variance, one value each per parameter).

Residual states - everything else: activations saved for the backward pass, temporary buffers, and memory fragmentation.

Here is the concrete number that motivates this entire post. Training with Adam in mixed precision, a common setup keeps two copies of the parameters (one FP16 copy for the fast forward/backward math, one FP32 "master" copy for the accurate weight update) plus FP16 gradients plus FP32 Adam momentum and variance:

Quantity Precision Bytes per parameter
Parameters (training copy) FP16 2
Gradients FP16 2
Master parameters (Adam) FP32 4
Momentum (Adam) FP32 4
Variance (Adam) FP32 4
Total - 16 bytes/parameter

A 7.5-billion-parameter model - roughly GPT-2 XL's scale - therefore needs 7.5B × 16 bytes = 120GB just for model states, before a single activation is stored. That single number is why none of the techniques below are optional at this scale; they are the only way the model fits at all.

Data Parallelism

Data parallelism (DP) is the simplest strategy and the one every distributed training run starts from. The idea: if the model fits on one GPU, just make copies of it.

GPU 1
full model copy
batch 1
GPU 2
full model copy
batch 2
GPU 3
full model copy
batch 3
  1. Split the global batch into N smaller batches (N = number of GPUs).
  2. Copy the identical model weights onto all N GPUs.
  3. Each GPU runs a full forward and backward pass on its own batch slice, independently.
  4. Because each GPU saw different data, each GPU now holds a different gradient.
  5. All-reduce: average the gradients across every GPU (sum, then divide by N), so every GPU ends up with the identical, averaged gradient.
  6. Every GPU applies the same weight update, so all copies stay in sync for the next iteration.

The step that makes this work is the all-reduce - a collective communication operation where every GPU sends its gradient to every other GPU and receives the sum back, done efficiently in a ring or tree pattern rather than N² point-to-point messages. This is the only communication DP needs per step, which is why it scales so well up to a point.

The wall DP hits: Data parallelism copies the entire model onto every GPU. If the model itself does not fit on one GPU - the 120GB example above on an 80GB A100 - DP alone cannot help, no matter how many GPUs you add. This is exactly the problem model parallelism solves.

Tensor (Model) Parallelism: Megatron-LM

The Intuitive Puzzle

Imagine NVIDIA hands you an 8-GPU node. Great! But your 70B parameter weight matrix is far too massive to fit on any single GPU. How do you split a single matrix multiplication across 8 GPUs without altering a single number in the final output - and without making GPUs wait on each other after every multiply?

Tensor parallelism, introduced in the Megatron-LM paper, solves this by splitting individual weight matrices across GPUs. This is called intra-layer parallelism because the partition happens inside one layer's math.

Consider a standard MLP layer computing Y = GELU(X · A), where input activations X have shape [batch, 4096] and weight matrix A has shape [4096, 16384]. There are two ways to split A across 2 GPUs - and only one avoids an expensive mid-layer synchronization bottleneck.

Method 1: Row-wise split of A (forces a mid-layer sync)

Split A by rows into A1 and A2 (each [2048, 16384]). To multiply validly, X must be split by columns: X = [X1, X2] where each X_i is [batch, 2048]. Each GPU computes a partial matrix product: 

GPU 0: partial_0 = X1 · A1   # [batch, 16384]
GPU 1: partial_1 = X2 · A2   # [batch, 16384]

# BAD: Neither partial output is valid until summed!
[ALL-REDUCE: sum partial_0 + partial_1 across GPUs]
Y = GELU(partial_0 + partial_1)   # Must wait for full sum before GELU can execute

Because GELU is a non-linear activation function, GELU(Z1 + Z2) ≠ GELU(Z1) + GELU(Z2). The partial products must be summed across all GPUs via an All-Reduce before GELU can run. This stalls execution smack in the middle of the layer.

Method 2: Column-wise split of A (the Megatron-LM breakthrough)

Instead, split A by columns: A = [A1 | A2] where A1, A2 are each [4096, 8192]. Now X ([batch, 4096]) is duplicated on both GPUs. Each GPU computes: 

GPU 0: Y0 = GELU(X · A1)   # [batch, 8192] - Complete, final output for cols 0..8191
GPU 1: Y1 = GELU(X · A2)   # [batch, 8192] - Complete, final output for cols 8192..16383

Because GELU applies elementwise, GELU(X · A1) is already the exact, correct final result for the first 8,192 columns. No partial sum is required, and zero communication happens!

The Paired MLP Architecture

Megatron-LM pairs this column-parallel first layer with a row-parallel second layer (which projects back from 16,384 to 4,096). Because layer 1's output is already sharded by column ([Y0 | Y1]), it feeds directly into row-split weight matrices B1, B2 without re-sharding. And because layer 2 has no non-linearity at its output, the partial product summation happens at the very end of the block in a single All-Reduce. 

[Input X] (Replicated: batch × 4096)
   │
   ├──► GPU 0: [X] @ [A1: 4096×8192] ──► GELU ──► [Y0: batch×8192] (Column Sharded) ──┐
   │                                                                               ├──► [Row-Parallel Layer 2]
   └──► GPU 1: [X] @ [A2: 4096×8192] ──► GELU ──► [Y1: batch×8192] (Column Sharded) ──┘
                                                                                   │
        GPU 0: [Y0] @ [B1: 8192×4096] = Z0 (Partial: batch×4096) ┐                 │
                                                                 ├──► [ALL-REDUCE (SUM)] ──► [Z Full] (Replicated)
        GPU 1: [Y1] @ [B2: 8192×4096] = Z1 (Partial: batch×4096) ┘
The "Aha!" Moment: Column-parallel takes replicated input and produces sharded output. Row-parallel takes sharded input and produces partial output that requires an All-Reduce. By pairing them back-to-back, Megatron-LM achieves full matrix parallelism with only 1 All-Reduce per MLP block!

Advanced Concept: Sequence Parallelism (Megatron-SP)

Standard Tensor Parallelism shards weight matrices in Linear layers, but leaves non-tensor-parallel regions - specifically LayerNorm and Dropout - replicated across all GPUs. For large models (e.g. Llama 3 70B), activations stored in these replicated LayerNorm/Dropout layers can consume over 30% of total memory.

Sequence Parallelism (Megatron-SP) eliminates this redundancy by sharding activations along the sequence dimension (S / N) during LayerNorm and Dropout.

Region Standard TP Activation Layout Sequence Parallel (SP) Activation Layout Communication Op
LayerNorm / Dropout Replicated ([S, H] on all GPUs) Sharded by Sequence ([S/N, H] per GPU) Reduce-Scatter
Column-Parallel GEMM Replicated Input → Sharded Output All-Gather input → Column GEMM All-Gather
Row-Parallel GEMM Sharded Input → Partial Output Row GEMM → Reduce-Scatter output Reduce-Scatter

The brilliant insight of Megatron-SP is that replacing 1 All-Reduce with 1 All-Gather plus 1 Reduce-Scatter transfers the exact same total byte volume over the network (2 × (N-1)/N × bytes). Sequence Parallelism gives you massive memory savings on activation buffers with zero added communication latency.

Hardware Interconnects: Why TP Stays Inside a Node

Why can't we just use Tensor Parallelism across 1,000 GPUs and call it a day? The answer comes down to hardware bandwidth constraints:

Interconnect Layer Technology Bidirectional Bandwidth Relative Speed
Intra-Node (GPU-to-GPU) NVIDIA NVLink 4 (H100) 900 GB/s 18x faster
Intra-Node Baseline NVIDIA NVLink 3 (A100) 600 GB/s 12x faster
PCIe Bus PCIe Gen5 x16 128 GB/s 2.5x faster
Inter-Node (Rack-to-Rack) InfiniBand NDR / RoCE v2 50 – 100 GB/s Baseline (1x)

Because Tensor Parallelism executes 2 All-Reduce operations per transformer layer, running TP across nodes over 50 GB/s InfiniBand causes the GPU compute cores to stall constantly waiting for network packets. TP is strictly restricted to an 8-GPU NVLink domain (1 physical node).

Pipeline Parallelism: GPipe

The Factory Assembly Line Analogy

Imagine an automobile factory with 4 specialized stations: Station 1 (Chassis), Station 2 (Engine), Station 3 (Interior), Station 4 (Paint). If Station 2 waits for Station 1 to assemble all 100 cars before touching an engine, 75% of your factory workers stand around idle. With micro-batching, the moment Car #1 leaves Station 1, Station 2 starts mounting its engine while Station 1 immediately begins Chassis #2.

Where Tensor Parallelism splits inside a layer, Pipeline Parallelism (GPipe) splits between layers (inter-layer). A 32-layer model on 4 GPUs places layers 1–8 on GPU 0, 9–16 on GPU 1, 17–24 on GPU 2, and 25–32 on GPU 3.

Micro-batching and Bubble Reduction

By splitting a batch into M micro-batches, GPipe keeps all pipeline stages busy concurrently: 

Time step:     1      2      3      4      5      6      7      8
GPU 0 (L1-8):   mb1    mb2    mb3    mb4    [FWD Done -> Start BWD]
GPU 1 (L9-16):  -      mb1    mb2    mb3    mb4    ...
GPU 2 (L17-24): -      -      mb1    mb2    mb3    mb4    ...
GPU 3 (L25-32): -      -      -      mb1    mb2    mb3    mb4

Because pipeline stages only transfer activation boundary tensors between adjacent GPUs once per micro-batch, the communication volume is minimal. This makes Pipeline Parallelism ideal for bridging across inter-node InfiniBand networks.

Activation Checkpointing

Pipelining micro-batches increases memory pressure because activations from multiple micro-batches must remain in memory simultaneously. Activation checkpointing resolves this by trading compute for memory:

  1. Store activations only at key block boundaries (checkpoints).
  2. Discard intermediate activations within the block during the forward pass.
  3. Recompute discarded activations on-the-fly during the backward pass starting from the checkpoint.

Mixed Precision Training

Mixed precision training (Micikevicius et al.) executes forward/backward math in FP16 or BF16 while maintaining an FP32 master copy of weights for optimizer updates.

Format Total bits Exponent bits Mantissa bits Key Characteristic
FP32 32 8 23 Full precision baseline
FP16 16 5 10 Prone to underflow; requires Loss Scaling
BF16 16 8 7 Same dynamic range as FP32; standard on A100/H100

DeepSpeed ZeRO: Removing Redundancy in Data Parallelism

Standard Data Parallelism redundantly replicates 100% of model states across all N GPUs. DeepSpeed ZeRO (Zero Redundancy Optimizer) eliminates this waste by partitioning model states:

Stage Partitioned State Across N GPUs Memory Per GPU (16 Bytes/Param Baseline)
Baseline DP None (100% Replicated) 16 × params
ZeRO-1 (Pos) Optimizer States (Momentum & Variance) 4 × params + (12 × params) / N
ZeRO-2 (Pos+g) Optimizer States + Gradients 4 × params + (14 × params) / N
ZeRO-3 (Pos+g+p) Optimizer States + Gradients + Parameters (16 × params) / N

Putting It Together: 3D Parallelism Configurator

Production training of frontier models (like Llama 3 70B/405B) combines all techniques into a 3D Parallelism grid. Here is how a real-world 256-GPU cluster (32 nodes × 8 GPUs/node) is configured: 

Global Cluster: 256 GPUs (32 Nodes × 8 GPUs/Node)

  ├── Tensor Parallelism (TP)   = 8   (1 Node; NVLink @ 900 GB/s)
  ├── Pipeline Parallelism (PP) = 4   (4 Nodes deep; InfiniBand @ 100 GB/s)
  └── Data Parallelism (DP+ZeRO)= 8   (32 Nodes / (1 × 4) = 8 DP Replicas)

Total Allocation = 8 (TP) × 4 (PP) × 8 (DP) = 256 GPUs

Why this configuration?

  • TP=8: Fits within a single 8-GPU NVLink node to handle the high-frequency All-Reduce communications at 900 GB/s.
  • PP=4: Splits 80 transformer layers across 4 nodes (20 layers/node), communicating activations across InfiniBand.
  • DP=8 + ZeRO-1: Replicates the 32-GPU TP+PP model 8 times to scale global batch size while sharding Adam optimizer states.

Key Takeaways

1. Model states (16 bytes/param) dominate memory. A 7.5B model needs 120GB before holding a single activation buffer.

2. Column-parallel paired with Row-parallel is the core of Megatron-LM. Column splitting avoids mid-layer non-linear synchronization, reducing communication to 1 All-Reduce per MLP block.

3. Sequence Parallelism (SP) shards non-tensor regions for free. By replacing All-Reduce with All-Gather + Reduce-Scatter, SP shards LayerNorm/Dropout activations with zero extra network traffic.

4. Interconnect speed dictates parallelism layout. High-frequency TP requires NVLink (900 GB/s), while PP and DP tolerate lower-bandwidth InfiniBand (100 GB/s).

5. 3D Parallelism is the production standard. TP handles intra-node layer splitting, PP handles inter-node depth splitting, and DP+ZeRO scales global throughput across thousands of GPUs.
